## Feedback

- When asked to make a manually-tuned layout "less constraining," don't assume removing pinned tables and letting the auto-solver refill is strictly better — verify the seat count numerically first. Confirmed 2026-08-01: unpinning a hand-built 10-table block dropped capacity from 156 to 140 seats in the same room, because (at the time) compact-mode auto-fill was a single uniform grid, less space-efficient than a hand-placed layout in an irregular room. Compact mode for rectangular tables no longer works that way — see the compaction-packing entry below — but re-verify numerically for round tables / spread mode, which still use the uniform grid.
- When a numeric result looks wrong to Larry, don't re-explain the same mechanism more insistently — re-derive it from the actual current state (fresh screenshot/DOM query) and check whether the premise itself is the flaw. Confirmed 2026-08-01: he called out an 8ft gap between a pinned head table and the first auto-placed row; correct diagnosis was that compact mode's *uniform-grid* algorithm was genuinely bad at sparse rooms (discarding a whole row over one obstacle clipping it), not that the gap was "necessary" — the fix was a real algorithm change ([[compaction-packing]]), not a better explanation of the old one.

## Project

- Added per-axis (`{ width, depth }`) `clearanceBuffer` support for rectangular table types in catalog.js/lib/geometry.js/lib/solver.js/app.js, plus `rect-8ft-rotated`/`rect-6ft-rotated` catalog entries (width/depth swapped). Why: rectangular banquet tables need much less clearance at their unseated short ends than along their seating edges; treating both axes as one scalar buffer (the old behavior) wasted a lot of usable floor. Round tables are unaffected (still a single scalar buffer, no axis distinction needed). Backward compatible: a plain number in a saved config's `buffer` field still applies to both axes.
- Added `presets/wedding-200-head-table.json` (manifest id `wedding-200-head-table`): 90x54 room, rect-8ft tables, a 3-piece pinned head table centered on the Fireplace obstacle, buffer `{ width: 12, depth: 24 }`, compact mode. Seats 204/200 using the solver's own defaults (Start X/Y = 0) — a head-table-centered-on-a-fixed-feature layout was flagged as "a VERY common ask" for this venue.
- `compaction-packing`: Added `compactRectPositions` in lib/geometry.js — a bottom-left-fill packer (candidate frontier seeded from room origin + every obstacle's corners, grown from each placed table's own corners) that compact mode now uses for rectangular tables instead of `squareGridCells`'s uniform lattice. Why: the uniform grid discards an entire candidate cell the moment any obstacle clips it at all, so a sparse layout (few tables needed) ends up on a rigid grid line far from existing furniture instead of hugging it. Round tables and spread mode are untouched (spread's even-coverage stride sampling still needs the uniform grid's uniform-coverage property; round tables keep their tuned hex/square choice). Real tradeoff measured in the 90x54 venue room: identical result for the actual 200-guest target (24 tables/204 seats, no regression), but the room's theoretical max capacity dropped from 244 to 212 seats, since greedy bottom-left-fill doesn't re-tile a fully-open rectangle as exhaustively as a uniform grid. Worth it here since 212 still clears 200 with room to spare — but if a future room ever needs to push closer to its true max capacity, the uniform grid may still win and could be worth offering as a fallback/option.
- Added a "Copy share link" feature (app.js): encodes the full config (same shape as the Configuration JSON box) into the URL hash fragment, with a visible readonly input as fallback if `navigator.clipboard.writeText` fails/is denied. On load, the hash is checked before falling back to `defaults.json`/presets. Deliberately uses the hash (never sent to a server) instead of a query string or a backend store — no server-side length limit applies, and GitHub Pages/no-backend stays true. Initial version was plain URL-safe-base64 (`#c=...`) — ~1.8KB URL for this venue's full 15-obstacle config. Larry found in practice that Apple Messages mangles/truncates a link that long (`#c=` format kept as a decode-only fallback for old links and for a browser without CompressionStream). Now gzips the JSON first via the native `CompressionStream('gzip')` Web API (`#z=...`, no dependency, shipped in every major browser since 2023) before base64-encoding: cut the same config's link from ~1.8KB to ~555 bytes (JSON compresses well here since obstacle objects repeat the same keys over and over).
- Added a 3D Walkthrough (`lib/scene3d-geometry.js`, `lib/scene3d.js`): first-person Three.js scene built from the same `room`/`tableType`/`result` the 2D SVG diagram already uses, opened via a button next to the diagram, dynamically imported so Three.js is never fetched unless it's actually opened. Explicit, scoped exception to the "no dependencies" rule (see CLAUDE.md), loaded via a CDN import map — no npm, no bundler. `lib/scene3d-geometry.js` holds the pure feet-based math (chair placement, collision) with no Three.js/DOM import, mirroring the existing `lib/geometry.js`/`lib/render.js` split. Chair placement determines the long (seating) vs. short (pushback) axis dynamically by comparing `dimensions.width` vs `dimensions.depth` rather than assuming `width` is always the long axis — required because catalog.js's `*-rotated` rect table entries swap which physical dimension is which, and the clearanceBuffer keys swap right along with them. Pinned-table obstacles (an obstacle with `seats > 0`) aren't `tableType` objects — they carry their own `width`/`depth`/`seats`/one scalar `buffer`, independent of any catalog entry (e.g. `wedding-200-head-table.json`'s "Head (4)" segments are 8ft rect bodies seating 4, not the catalog's 8) — handled via a separate adapter (`chairInputForPinnedObstacle`) rather than trying to look up a matching catalog entry.
- Verifying this in a remote/sandboxed session: outbound network to CDN hosts (unpkg, jsdelivr, esm.sh, cdnjs) is proxy-denied from this kind of sandbox, so a headless browser here can't load the real CDN-hosted Three.js. Worked around it for verification only (never committed) by `npm install three@<version>` locally (registry.npmjs.org *is* reachable — it's allowlisted) and temporarily pointing the import map at the installed package's files served over the same local `http.server`, using the pre-installed Chromium (`/opt/pw-browsers/chromium`) via a scratch-installed `playwright` to actually render the scene, screenshot it, and confirm dispose/reopen didn't leak canvases — then reverted the import map back to the real CDN URLs before committing. Worth remembering next time a CDN-loaded dependency needs real verification from one of these sessions.
